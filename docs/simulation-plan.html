01 / RECOMMENDATION

One page. Several experiments. A separate simulation engine.

Build a new React + TypeScript + Vite workbench with an imperative Three.js viewport and a dedicated Web Worker for the reference simulation. Start with WebGL 2 rendering; keep rendering behind a small interface so WebGPU can be evaluated and adopted when a measured workload warrants it.

Why this combination

The main task is custom geometry: paired dipoles, selectable shells, field lines, trajectories and slices. Three.js provides a suitable rendering toolkit without imposing a game physics model. React handles scenario controls, inspectors and experiments; particle updates stay outside React.

What “single page” means

One persistent workspace with scenario presets and contextual panels. Separate source modules and worker bundles are expected. Start with static hosting, local preset files and no server dependency. Small plots can use SVG; add a chart library only if richer analysis needs it.

Fresh architecture is explicitly allowed. The existing app is historical context, not a migration constraint. The recommendation follows the required visuals and current evidence. Retaining Three.js would not mean retaining the old worker, GUI or simulation loop.

This deliverable contains the preserved blueprint, this plan and a disposable renderer experiment. No application scaffolding, dependencies or production implementation have been added.

Medium lifecycle

Control the seed, represented density, frequency band, lifetime convention and playback rate. Inspect a dipole’s age, energy and orientation. Compare the medium’s energy ledger before and after a birth/death cycle.

Provide play/pause, single fixed step, reset to seed, speed control and camera presets. Editing a model parameter applies at a known simulation tick and creates an event record. Scrubbing uses checkpoints and deterministic replay. Camera and layer changes do not alter the experiment.

On narrower screens, move the library and inspector into drawers. Include keyboard controls, visible focus, textual probe readouts, charge symbols alongside colour, and a reduced-motion mode with stepping and muted flashing.

04 / MODEL DECISIONS

Specify the mathematics before claiming fidelity.

The source provides constraints and geometric interpretations, but not a closed numerical model. The following decisions are part of the first implementation milestone. Any temporary illustration must expose its chosen rule.

Decision neededProposed treatmentWhat closes it
Force, torque and pressure lawsRequire explicit F(r, orientation), torque, density-to-pressure relation, coupling constants, boundary conditions and short-range regularization. Do not invent a solver from the name “London–van der Waals”.Documented equations with units, stable two-body fixtures and an energy-transfer convention.
Constants: emergent or constrained?Keeping Z₀ exactly 376.73 Ω is a calibration constraint, not an independent prediction. Distinguish imposed values from computed response. Keep the source value as its own model parameter.A specified derivation for ε₀ and μ₀ plus tolerances. NIST gives 376.730313412 Ω with uncertainty; it is not the source’s exact rounded value. [7]
Energy/lifetime conventionThe blueprint’s E = hf/2 and ΔE Δt = h/2 imply Δt = 1/f only if ΔE = E. That identification, equality and h versus ℏ convention must be explicit. Birth/death balancing needs a medium reservoir; matching average counts is insufficient.Agreed lifetime distribution, frequency cutoffs and local energy debit/credit rules.
Scale and numerical resolutionUse normalized coordinates per experiment, a finite representative sample and documented physical-to-display scale. A length span of roughly 10²³ from Planck to electron Compton length implies roughly 10⁶⁹ uniform 3D cells, before adding larger scales.Domain size, particle weight, frequency bands and accuracy target for each preset. No literal Planck-resolved universe.

First boundary: a reproducible, parameterized visualization can be built once the reduced rules are specified. Predictive physical fidelity remains conditional on equations, numerical validation and comparison with evidence.

Investigation A · actual renderer experiment

Open the disposable spike to compare two instanced lobes against one coarse point per dipole, at 1,000 / 10,000 / 50,000 dipoles. It uses pinned Three.js 0.185.1, the npm version resolved during this investigation, independently of the old app’s 0.163.0.

Local evidence

10,000 paired dipoles · 2 draw calls · 10.0 ms median frame interval. One valid WebGL sample on an AMD RX 7900 GRE / Chromium 150 produced 500 intervals, with p95 10.1 ms, at a 1265 × 416 canvas and DPR 1. WebGPU and its forced WebGL fallback passed explicit frame-submission checks; 50,000 coarse points also submitted on WebGL and WebGPU.

Measurement results and limitations are recorded in the investigation notes and the machine-readable results. A first preview timing attempt was invalidated by visibility/resize and discarded. Later preview animation stalls prevented valid WebGPU timing comparisons. These are device-specific observations, not production frame-rate promises.

Measure with the tab visible, unchanged viewport, one second of warmup and five seconds of sampling. Export backend, GPU description when exposed, count, representation, viewport, draw calls, frame count and frame-interval percentiles. The spike uses CPU animation and opaque materials. It does not measure the physics worker, neighbor search, transparency, field lines, picking, volumes or GPU compute.

Investigation B · representation and data budget

Two 4×4 Float32 matrices cost 2 × 16 × 4 = 128 bytes/dipole: 1.28 MB per 10,000-dipole snapshot, or 38.4 MB/s at 30 snapshots/s, before copies and GPU uploads. A proposed packed position + quaternion + size format is 8 floats, or 32 bytes/dipole. Those are analytical payload sizes, not measured throughput.

Use detailed paired geometry only where its orientation can be read. Use point samples for distant density, and aggregate pressure into a coarse grid. A 64³ grid with four Float32 channels is 4 MiB per buffer (8 MiB when double-buffered); choose grid resolution independently from particle count. Instancing reduces draw calls, not O(N²) force evaluation.

Historical code findings — useful lessons, no migration obligation

The old app has two instanced meshes, a 400-dipole cap, dat.GUI and transferred matrix arrays. The first three sliders lack their own worker-update callbacks. Birth logic admits at most one dipole per update, so the creation-rate label does not hold at high rates. The worker allocates replacement buffers after transfers despite returning earlier ones, and uses unseeded randomness and variable elapsed time. A future implementation should specify ownership, fixed ticks and reproducibility afresh. These are source-inspection findings, not newly fixed defects.

Simulation contract

Use initialize, step, setParameters, serialize and restore operations. Commands carry sequence IDs; worker replies include the applied tick and parameter version. Keep model code independent of the DOM and renderer.

Represent positions, orientations, ages and energies in typed arrays. Use Float64 arithmetic where required in the CPU model and normalized Float32 snapshots for rendering. A seeded generator plus saved generator state supports exact replay within the same model/runtime.

Time and ownership

Fixed model timestep, separate render clock and bounded catch-up. Display slowdown rather than silently changing model accuracy. Pause when the page is hidden, with an explicit resume policy.

Use a bounded pool of transferable snapshot buffers with clear owner states and backpressure. Recycle acknowledged buffers; do not queue unbounded snapshots. Start without SharedArrayBuffer or cross-origin isolation requirements.

Rendering layers

Medium, polarization vectors, pressure slice, shells, photons, events and annotations have independent toggles. Clamp device pixel ratio; use geometry instancing, pooled objects and level of detail. Update field lines and plots at a lower frequency.

Support clipping planes, camera presets and selection using a coarse spatial index before detailed picking. Prefer cutaway shells over heavy overlapping transparency.

Save, compare and recover

Versioned JSON stores model ID/version, seed, generator state, units, parameters, simulation tick, events, checkpoints and view state. CSV exports diagnostics; PNG exports a labelled view. Validate imported sizes, ranges and schema versions.

Worker errors stop the run with a visible diagnostic. Context/device loss allows reinitialization from a checkpoint. A missing graphics backend leaves documentation and readouts usable.

React owns UI state and connects to the renderer through lifecycle hooks and refs; do not create a React component per dipole or write every frame into React state. Vite supports TypeScript and module workers; run a separate TypeScript type check in validation. [8] [6]

07 / DELIVERY SEQUENCE

Deliver inspectable slices of the model.

Stages below are ordered by dependencies. All implementation stages remain pending. Resolve each stage’s equations before estimating its solver effort; rendering can progress with clearly labelled analytic fixtures.

0

Model specification and design baseline

Normalize notation in a separate specification while preserving the source. Resolve the decisions in section 04, starting with lifecycle, units, sampling and energy accounting. Choose desktop/browser targets and baseline scenario size.

Exit: equations, approximation labels, parameter schema, known-answer fixtures and agreed acceptance budgets. This is the next work after review.
1

Workbench foundation

Create the new app, viewport adapter, accessible controls, worker protocol, fixed-step clock and deterministic empty scenario. Add play/pause/step/reset, seed and error states.

Exit: replayable state, acknowledged parameter changes, backend failure handling, responsive layout and no duplicate workers/render loops.
2

First useful release · medium laboratory

Implement the agreed fluctuation lifecycle, frequency/energy mapping, near/far representations, individual inspection and the medium energy ledger. Add save/load, diagnostics export and representative quality presets.

Exit: one complete experiment that can be controlled, explained, saved and reproduced; seeded statistics and energy bookkeeping pass. This is the MVP.
3

Polarization and mechanical response

Add stationary/moving polarizers, E/B orientation, medium torque, pressure sampling, two-source interactions and force probes. Compute constants only where the agreed laws support it.

Depends on stages 0–2 and explicit force laws. Exit: sign/orientation fixtures, stable response and convergence checks; every plotted field comes from the model or a labelled fixture.
3a

Casimir effect · parallel plates

Build an adjustable-gap conducting-plate scene with inside/outside field views, mode overlays and force/energy curves. Start with an explicitly ideal analytic reference; add a zepton prediction only after boundary and spectral-energy rules are defined.

Exit: attractive force, inverse-fourth-power gap scaling, energy-gradient consistency and documented idealizations. Read the Casimir experiment specification. Planned; not yet implemented.
4a

Light through the zero-point field · planned

Visualize light as a travelling energy wave through successive induced, counter-rotating pairs. Show local rotation, separation and collapse at fixed centres, surrounding electric polarization and magnetic rotation, a wave overview and a pair close-up. Step induction events; inspect wavelength, phase, travel time and pair/field energy.

Based on Fleming’s photon paper, especially §§2, 4–6. Begin with a labelled illustrative sequence; quantitative induction and timing rules gate a calculated response. Exit: correct handoffs, fixed centres, reproducible phase/travel and energy accounting. Read the light experiment specification. Planned; not yet implemented.
4b

Particle shell experiments

Add nested shell cutaways, species presets and excluded-energy calculations.

Depends on medium/polarization and specified spectral rules. Exit: radius constraints, finite energy integrals, shell diagnostics and clear time scaling.
5

Exchange events and conservation

Implement the approved event maps, jumping trajectory, absorption and beta-decay illustration. Add timeline checkpoints, event stepping and complete before/after ledgers.

Depends on shells and event rules. Exit: replay reconstructs the same events; medium plus particles balance within stated tolerances.
6

Cosmology, advanced rendering and release

Create a separate scaled tired-light experiment after obtaining its loss law and comparison data. Profile full workloads; add WebGPU compute or volume rendering only if justified. Complete browser/accessibility checks and static deployment packaging.

Cosmology does not gate the medium MVP. Exit: traceable comparison data, measured capability tiers, documented model limitations and a reproducible release build.
08 / ACCEPTANCE CRITERIA

Prove control, reproducibility and numerical behaviour.

AreaProposed acceptance gate
Control and replayPause changes no model state; step advances exactly one tick; reset with the same seed yields the same reference run. Parameter changes are acknowledged at a tick. Save/load + replay reproduces state and events within documented numeric tolerances.
Numerical correctnessUnit-consistent equations; no NaN/Infinity; lifecycle distributions match specified statistics; source-sign/right-hand fixtures pass. Compare dt, dt/2 and resolution changes. Use combined absolute/relative conservation tolerances, chosen in normalized units at stage 0, including the medium reservoir.
Performance targetProvisional desktop gate: a 10,000-dipole medium scene at 1280×720, capped DPR 1.5, median frame interval ≤16.7 ms, p95 ≤33.3 ms and control acknowledgement p95 ≤100 ms. Identify the reference device before making this a release guarantee. Measure the full worker + renderer scenario for 30 seconds after warmup.
Compute and memoryWorker step p95 below its wall-clock budget at 1× playback, without unbounded catch-up. Track snapshot latency, allocation and heap/GPU resource trends through ten minutes and repeated scenario switches. Lower visual quality without silently altering simulation parameters.
Compatibility and recoveryTest current target Chrome/Edge and Firefox/Safari where available on real hardware. Exercise WebGL 2, WebGPU availability/null-adapter/failure, context loss, worker restart and tab hide/resume. Rendering fallback does not imply compute fallback. Verify imports over localhost/HTTPS. [5]
Interaction and accessibilityKeyboard access to controls and selection alternatives; readable charge signs and unit legends; reduced motion; no clipping at mobile widths; explicit invalid-input feedback. Run browser flows for scenario selection, step, edit, reset and export/import.
Engineering checksType check, production build, meaningful model/worker tests and browser smoke tests. Validate checkpoint schema versions and buffer ownership. Run GPU benchmarks on hardware; software/headless runs can verify function but do not establish hardware performance.

Investigations still needed before advanced features

A combined pressure-slice + streamline + cutaway scene; worker transfer latency with packed snapshots; neighbor-search scaling; a small CPU-versus-WebGPU compute parity test; and performance on an integrated GPU. These are explicitly unmeasured. The current spike narrows the renderer choice without claiming to settle those questions.
