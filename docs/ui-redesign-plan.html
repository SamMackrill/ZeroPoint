ZeroPoint · UI redesign plan · 29 Sep 2026

One workbench for every experiment: clean by default, powerful when you need it

The five laboratories (Medium, Light, Electron, Casimir and van der Waals) each grew their own layout, wording and controls. This plan replaces them with a single, fixed, app-style research workbench. The 3D view always stays on screen. Controls, readouts and time are always in the same place. Explanations appear only when you ask for them.

02

Current UI audit

This audit comes from reading src/app/App.tsx, src/light, src/electron, src/casimir and src/van-der-waals on main at f127d6b, and from screenshots at 1440×900.

Structure

  • Five layouts. Medium is a fixed 3-column app. Light and Electron are long scrolling pages, and Electron › Spin is 3,424 px tall. Casimir and van der Waals each have their own heading, mode cards, card grid and footer.
  • Lopsided navigation. Medium is home and experiments are listed only in its sidebar. Other labs go back with "← Medium laboratory" or "← Experiment library". The roadmap entry "Beyond the medium" still lists Casimir as planned.
  • The viewport scrolls away while you use the timeline, probe chart or shell controls lower on the page. You can't see cause and effect together.
  • Scenario-like variants have four treatments: Medium presets are sidebar buttons, Electron modes and Casimir pairings are big cards above the toolbar, and van der Waals stages are numbered step cards.

Controls

  • Transport wording varies: "Run" / "Run light" / "Run electron" / "Run dipoles", and "Next induction" / "Advance 1 τ". Speed options differ (Casimir uses 0.1–2×). The Space kbd hint appears in only two labs, and van der Waals has no keyboard control.
  • Files vary: "Save experiment" / "Save light" / "Save electron". Checkpoints appear in three places with three styles and limits (6, 4, 4).
  • Two apply models with no signal of which applies. Medium is live. Light and Electron need a form submit, and an unsaved slider looks the same as an applied one.
  • The Electron velocity slider is disabled outside Moving mode, when it should be hidden.
  • Selection requires a "Zepton selector" checkbox in Electron only.
  • Layers use toggle switches in Medium and checkboxes elsewhere. Reduced motion is repeated in each lab.

Reading load

  • Caveat paragraphs (light-small) under almost every card. Electron alone has about 20.
  • Large metric tiles repeat values also shown elsewhere. "Propagation speed 1.000 c" never changes.
  • Static reference cards (Scale & conventions, Source constants, Source papers) take permanent space.
  • Header clutter: "Field Laboratory", v0.1 chip, "Runs locally" badge, dev-plan link, sidebar tagline and Model-note card.

Visual system

  • 484 unique hex colours across seven stylesheets, with no tokens beyond --mint, --muted and --line.
  • 25 font sizes, with 282 declarations below 11 px, 186 of them below 10 px (recounted in UI 01g to include the font shorthand, which the first count missed). These are hard to read and fail at a normal viewing distance.
  • Light and Electron share light-* class names. Electron imports light.css, so styles are coupled by accident.
  • Five hand-rolled SVG plot implementations (Medium, Light, Electron, Casimir pressure history, van der Waals gap sweep) with different axes, labels and colours.
03

Design principles

1 · The field is the work

The viewport is always visible and never scrolls. Every other element exists to change it or measure it.

2 · Same thing, same place

Time is always bottom-centre. Settings are always on the right. Where you are is always on the left. Files are always top-right. Wording is identical across experiments.

3 · Show only what applies

Hide controls and layers that don't apply to the current scenario rather than disabling them. Scenario defaults decide what's on.

4 · Quiet by default, deep on demand

No paragraphs in the workspace. Each ⓘ opens exactly the caveat for that control. The About sheet holds the full context.

5 · State is always legible

You can always see whether it's running or paused, whether a change is applied or pending, what's selected, and what B is being compared against.

6 · Everything reachable by keyboard

Each action has one registry entry that drives the buttons, shortcuts, command palette and URL state together.

Rules

  • Switching scenarios within an experiment restarts it (paused at tick 0). When it's configured, this is announced with a toast that offers Undo.
  • Switching experiments preserves each experiment's state, as today. Playback pauses.
  • Once you edit a parameter, the scenario label becomes Balanced medium · modified, replacing the hidden 'custom' preset. "Reset to scenario" is available in Setup.
  • Planned items open a small popover with a one-line summary and a link to docs/planned-experiments/*.md. They never open a workbench.
  • The breadcrumb in the header mirrors the selection: Electron › Spin in the field.
  • URL: #/electron/spin?…. See URL state.

Panel behaviour

  • Use react-resizable-panels for the rail, the inspector and the viewport/dock split. Sizes and collapsed state persist in localStorage for each experiment.
  • Focus mode (Ctrl .) collapses the rail, inspector and dock at once, leaving the header, viewport and timeline. Pressing it again restores the previous sizes.
  • Only the inspector body and dock body scroll. The page itself never scrolls (height:100dvh; overflow:hidden).
  • The status bar (22 px) shows only the run state, seed or configuration hash, tick, and the model disclaimer. FPS, worker ms/step, WebGL version and model ID appear only when Settings › Show debug telemetry is on.
06

Core research workflow

The layout is ordered to follow the loop you actually run: left to right, then down.

1 · ChooseScenario in the rail, or Ctrl K, or a shared URL
2 · ConfigureSetup tab. Live parameters apply now, ↻ parameters wait for Apply
3 · Run & scrubTimeline bar: Space, →, ], or drag the scrubber
4 · SelectClick in the viewport. The Selection tab and 2-up pane follow it
5 · MeasureDock plots, probe, ledger and events
6 · Capture & compare◆ Capture, then pin as B
7 · KeepSave, Export, or Copy link
A full loop needs no page scrolling and no explanatory text. Every step has a keyboard path, and every step leaves visible state behind: markers on the timeline, a "modified" scenario label, a B badge, and a pending bar.

Info layer & copy

ⓘ InfoTip

Attached to a parameter, layer or readout label. One or two sentences of caveat, plus an optional "More in About ›" link. It opens on click or Enter, and Esc closes it.

Example, Turn gain: "Magnifies each local turn for visibility. Display only; does not change the model."

About sheet

Opened from the header "Illustrative model" chip, Help › About this scenario, or Shift ?. It slides over the inspector and has four sections: This scenario (what you're seeing and its assumptions) · Units & constants · Sources (papers, video timestamps) · Saved views.

Copy rules

  • Labels are 1–3 words, with units in the value field and not the label.
  • No sentences in the workspace. Empty states are the one exception (one line).
  • "Illustrative" appears once, in the header chip, not per card.
  • Use the same verbs everywhere: Run, Pause, Step, Reset, Capture, Apply, Revert, Load, Save, Export.

Existing caveat text isn't deleted. It moves verbatim into About › This scenario, grouped per scenario, so no scientific qualification is lost, and the edit pass can happen later.

Runtime adapter

Worker vocabularies differ today (Medium uses running and parameters; Light and Electron use run, configure, next and advance). One adapter exposes run(bool), step(), jump(τ), nextEvent(), seek(tick), reset(), speed(x), setLive(params), configure(params), checkpoint() and restore(c). Unsupported commands report capabilities, which drive the timeline bar's enabled state. The worker protocols themselves don't change. Casimir and van der Waals run on the main thread (a rAF loop and an interval). A MainThreadRuntime driver wraps them with the same fixed-step accumulator and hidden-tab pause, so the shell treats all five experiments alike.

New dependencies

  • @radix-ui/react-{tabs,toggle-group,slider,popover,dropdown-menu,dialog,tooltip,collapsible,scroll-area}: headless and tree-shaken.
  • cmdk: command palette.
  • react-resizable-panels: resizable and collapsible panels with persistence.
  • No styling library. Plain CSS with tokens, co-located per component, replacing the minified single-line stylesheets.

Branches & worktrees

  • One worktree per open layer at C:\Users\Sam\ZeroPoint-wt\NN-slug, created from its base: git worktree add ../ZeroPoint-wt/07-medium -b ui/07-medium ui/06-shell
  • Each worktree runs npm ci, and its dev server and e2e use port 5200 + NN via ZP_PORT. Worktrees never share a server.
  • The primary checkout stays on main and is used only for fetch, merge follow-up and plan edits.
  • After a merge, the worktree is removed and the branch deleted, locally and on the remote.
  • Window: at most 4 unmerged layers. When the window is full, the babysitter stops starting new layers and spends its time on fixes and restacks. This bounds restack cost and conflict risk.
  • Restacking goes layer by layer, inside each layer's own worktree: git rebase --onto <base> <recorded base SHA>. git rebase --update-refs can't be used, because it skips branches checked out in other worktrees. stack.mjs records each layer's base SHA so the rebase is exact. Pushes use --force-with-lease.
  • State lives in $(git rev-parse --git-common-dir)/ui-stack/state.json. It is shared by all worktrees and never committed.

Review-gate scheduler

readyChecks green, pushed, PR open
queuedWaiting for the hourly slot
triggered@coderabbitai review posted

fixingFindings addressed in one push
cleanNo open findings
merge-readyClean, green, base merged
  • One global slot: the next trigger is allowed at lastTriggerAt + 60 min + 3 min buffer. If CodeRabbit replies with a rate-limit notice ("Please wait N minutes…"), the wait is parsed and the slot is moved accordingly.
  • Priority when the slot opens: first, the lowest queued PR in the stack, because merges go bottom-up and fixes low in the stack ripple upwards. Second, re-reviews ahead of first reviews at the same height.
  • Command: gh pr comment N --body "@coderabbitai review" (incremental). @coderabbitai full review is used only when a rebase onto a squash-merged main rewrote the whole diff.
  • Completion: a review exists from coderabbitai[bot] with commit_id == head, or the summary reports no actionable comments for that SHA. With no response after 90 minutes, the PR is re-queued once, then escalated.
  • Never waste a slot:
    • Never trigger on red local checks, and batch every fix for a review into one push.
    • Fixes that are purely nitpicks, docs or renames are answered and resolved without a re-review. Re-review is requested only when a fix changed behaviour.
    • An upper layer keeps its clean state through a restack if git range-diff shows its own commits unchanged.

Babysitter loop

The babysitter runs as a self-paced Claude Code /loop driven by a project skill, .claude/skills/babysit-ui-stack/SKILL.md. The mechanical helper scripts/stack.mjs provides status, trigger, restack, retarget and nav. Both ship in UI 00. Each wake:

  1. Sync: git fetch --prune, then reconcile state with GitHub: merges, new reviews, new comments, rate-limit replies, CI status.
  2. Merged bottom PR: retarget the next PR to main (gh pr edit --base main). Rebase it with git rebase --onto origin/main <recorded base SHA> (stack.mjs retarget), restack the layers above it (stack.mjs restack), force-push with lease, refresh the navigators, and remove the merged worktree.
  3. Reviewed PRs: triage every open CodeRabbit thread (table below) and fix. Run the checks, push once, reply on each thread with the commit SHA, and resolve it (GraphQL resolveReviewThread).
  4. Restack: if a lower branch moved, rebase the layers above it, re-run checks on each changed layer, and push.
  5. Trigger: if the slot is open, request a review for the highest-priority queued PR and record the time.
  6. Build ahead: if the window has room, implement the next layer in a new worktree, pass the checks, and open its PR (queued).
  7. Report: mark merge-ready PRs, post a push notification, and register every PR with this thread.
  8. Sleep: wake at the next slot time if something is queued, otherwise in 20–30 minutes. When blocked on a user merge or decision, use a 60-minute heartbeat.

Each push to a layer that CodeRabbit has already reviewed starts another review, and each review costs an hourly slot. When a layer's findings keep coming, the UI work behind it stalls. So once a layer has been reviewed, every new finding is sorted into one of two kinds:

Blocking: fix in placeWrong behaviour in the app; a broken test or CI; data loss; a real security exposure; anything that would make merging this layer, or anything the babysitter does on its behalf, unsafe (e.g. a merge-readiness check that can pass too early).Fix in the layer, push once, reply with the commit, resolve.   • Judgement first. When in doubt, a finding is blocking. A deferral must be safe: nothing on main may depend on a deferred fix to be correct.
  • The remedial layer is an ordinary stack layer named ui/NN<x>-remedial-<topic> (e.g. ui/01h-remedial-tooling), opened at the top of the stack. It never forces a restack of reviewed layers. Its PR body keeps the checklist, with a link to each deferred thread. It is reviewed and merged in turn like any other layer, and a new one is opened when the next batch of deferrals starts.
  • Freeze reviewed layers. Improvements to the stack tooling that no finding asked for also go into the topmost unreviewed layer, never into a layer under review. stack.mjs runs from that layer's worktree, whose copy is the newest.

Quality gates on every push

Locally, and in CI from UI 00: npm run check · npm test · npm run test:e2e (on the worktree's port) · npm run build. In addition: JSDoc on new and touched functions, no hex colours outside tokens (from UI 01), and the bundle-size delta recorded in the PR body (from UI 02).

Freeze, milestones & deploys

  • Main freeze: no UI or experiment changes merge to main outside the stack until UI 18 lands. Docs and papers are fine. If an unexpected src/ change appears on main, the babysitter restacks and notifies you rather than absorbing it silently.
  • Deploy milestones (npm run deploy from an up-to-date main, after all checks pass): M1 after UI 07 (the shell and Medium), M2 after UI 11 (every lab in the shell), and M3 after UI 18 (done). Nothing is published in between.
  • Design gates: UI 01d paused for your approval of the palette preview before UI 01e applied it. Since then, every layer that visibly changes the UI is built, reviewed and CI-checked as normal, but held (stack.mjs hold) until you approve its before/after page of real screens. The approval is asked with the question tool. Layers above a held one keep moving; only its merge waits.

Merging & throughput

Merging

Squash merge, bottom-up, by the babysitter: stack.mjs merge merges the bottom PR only when it targets main, CodeRabbit is clean and CI passes. It pins the reviewed head commit, then retargets and restacks the next layer and removes the merged worktree and branch. You can still merge by hand at any time.

Throughput

25 PRs at about 1.5 review slots each is roughly 38 slots, so about 38 hours of wall time are gated by CodeRabbit, however fast the coding goes, plus the palette approval. Implementation runs ahead inside the 4-layer window, and babysitter merges keep the pipeline moving.

Open questions & risks

To decide during build

  • Medium backward seek. Should Medium keep an automatic checkpoint ring (e.g. every 1 τ) so the open-ended track can scrub backwards? It's cheap in memory at 10k dipoles, but needs a small worker addition.
  • Probe placement. Should Alt-click in the viewport place the Electron probe (↻, staged)? It would be natural for a researcher, but it's a new interaction.
  • Light scenarios. Should Light get named scenarios (e.g. "Short wavelength", "Reverse direction") or stay a single leaf?
  • Palette approval at UI 01d: the tokens preview shows every current colour next to its proposed token.
  • Dock default per scenario. The proposal is Plots for Medium and Light, Shell rates for Spin, and Probe for Stationary and Moving.

Risks

  • E2E churn in P3 and P4. About 300 getBy… calls across five specs reference current labels. UI 01c moves them onto stable roles and test IDs first, and test updates land in the same PR as each migration.
  • Review throughput. The hourly CodeRabbit gate, not implementation, sets the pace (about 38 hours). The session must be running for the loop to progress.
  • Renderer picking. Click-vs-drag needs a change in each of FieldRenderer, LightRenderer and ElectronRenderer, plus the Casimir SVG scene. Test with software-rendered Chromium.
  • Keyboard conflicts with OrbitControls, which may listen for arrow keys. Scope OrbitControls keys to the focused canvas only.
  • A/B for Medium doubles CPU use. Pause B when the tab is hidden and when the Compare tab is closed.
  • Bundle size. Radix, cmdk and resizable-panels add roughly 40–60 kB gzip. That's acceptable next to Three.js, but should be measured in P0.
